# Tópico de telemetria bruta (3 partições, Fator de Replicação 3)
docker exec -it kafka1 kafka-topics --create \
  --bootstrap-server kafka1:29092 \
  --topic eventos-rede-primitivos \
  --partitions 3 \
  --replication-factor 3

# Tópico de eventos derivados (1 partição, Fator de Replicação 3)
docker exec -it kafka1 kafka-topics --create \
  --bootstrap-server kafka1:29092 \
  --topic eventos-rede-derivados \
  --partitions 1 \
  --replication-factor 3

Configuração Geral (Configs)

PartitionCount: 3 — O tópico foi dividido em 3 fatias paralelas (partições 0, 1 e 2) para permitir o processamento simultâneo de dados.

ReplicationFactor: 3 — Existem 3 cópias completas de cada partição espalhadas pelo cluster.

min.insync.replicas=2 — A regra de segurança que exige a confirmação de gravação em pelo menos 2 brokers ativos antes de dar o retorno para gravações com acks=all.

Métricas de Cada Partição

Partition (0, 1, 2): O número identificador da fatia do tópico.

Leader (3, 1, 2): O ID do broker responsável por processar todas as conexões de escrita (Produtor) e leitura (Consumidor) daquela partição específica. O Kafka atribuiu os líderes de forma equilibrada:

Partição 0 -> Líder é o Broker 3

Partição 1 -> Líder é o Broker 1

Partição 2 -> Líder é o Broker 2

Replicas (ex: 3,1,2): A lista de todos os brokers atribuídos para guardar uma cópia dessa partição, independente de estarem online ou offline no momento.

Isr (In-Sync Replicas): A lista dos brokers que estão vivos, funcionais e 100% sincronizados com o líder em tempo real.

Como o campo Isr contém exatamente os mesmos três números listados em Replicas para todas as partições, seu cluster não possui nenhuma réplica atrasada ou fora do ar.

docker exec -it kafka1 kafka-topics --describe \ 
  --topic eventos-rede-derivados \
  --bootstrap-server kafka1:29092

Paralelismo no Consumo (Escalabilidade Horizontal): Permite que múltiplos consumidores dentro do mesmo Consumer Group leiam dados em paralelo. Com 3 partições no tópico primitivo, você pode rodar até 3 instâncias simultâneas do processor.py — cada uma dedicada a uma partição exclusiva sem duplicação de dados.

Maior Vazão de Escrita (Throughput): Produtores não ficam gargalados em um único servidor. Como os líderes das partições são distribuídos entre os brokers (kafka1, kafka2, kafka3), a gravação de mensagens aproveita a CPU, memória e largura de banda de toda a infraestrutura ao mesmo tempo.

Balanceamento de Armazenamento: Evita que a capacidade de disco de um único nó seja ultrapassada. Um tópico com terabytes de dados pode ter suas partições espalhadas entre dezenas de servidores do cluster.

Garantia de Ordem Granular (por Chave): O Kafka garante a ordem sequencial estrita das mensagens dentro da mesma partição. Utilizando o ASN como chave de particionamento, todos os pacotes de uma mesma rede cairão na mesma partição, mantendo a cronologia exata para análise da janela deslizante.

Como Desligar o Cluster

Desligamento temporário (Recomendado no dia a dia):

Bash
docker compose stop
Paralisa a execução de todos os contêineres mantendo o estado interno intacto.
(Dica: para desligar apenas um broker específico durante testes, use docker stop kafka2).

Desligamento completo (Destrói os contêineres e a rede virtual):

Bash
docker compose down
Encerra e remove os contêineres e a rede criada pelo Docker, garantindo um ambiente limpo para reiniciar do zero na próxima execução.

Como Ligar o Cluster

Se você usou o docker compose stop anteriormente:

Bash
docker compose start
Religa rapidamente os contêineres existentes que estavam pausados.

Se você usou o docker compose down (ou para subir o cluster pela primeira vez):

Bash
docker compose up -d
Recria e inicializa os 4 contêineres (zookeeper, kafka1, kafka2 e kafka3). A flag -d executa o processo em segundo plano (detached mode), liberando o seu terminal imediatamente.

Como Verificar o Status do Cluster

Bash
docker compose ps
Exibe o estado de saúde da aplicação. Todos os 4 serviços devem ser listados com o status Up ou Running.
